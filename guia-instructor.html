💡 Menciona ahora, no después: más adelante en el taller vamos a agregar "deny": ["Write(.claude/settings.json)"] a los permisos. Demo en vivo - Configurar permisos 
{
  "permissions": {
    "allow": [
      "Bash(python:*)",
      "Bash(pytest:*)",
      "Read",
      "Write(src/**)",
      "Edit(src/**)"

      "Bash(rm -rf:*)",
      "Write(.env*)"
    ]
  }
}

💡 Punto clave: Explica que allow reduce los prompts de confirmación. Sin embargo, deny es absoluto - Claude no podrá hacer esas acciones aunque quiera.

🔍 Deep Dive: Patrones glob en permisos
▼
  • * - Cualquier cosa en ese nivel
  • ** - Cualquier cosa en cualquier nivel de subdirectorio
  • Bash(comando:*) - Cualquier argumento para ese comando
  • Write(src/**/*.py) - Solo archivos .py dentro de src/

4 Hooks - PreToolUse y PostToolUse

20 min ▼
⏱️ Distribución: 5 min concepto | 10 min demo | 5 min práctica
Qué decir al comenzar

"Si los Skills son cosas que invocamos, los Hooks son cosas que siempre suceden automáticamente. PreToolUse intercepta ANTES de que Claude ejecute algo - perfecto para validación. PostToolUse actúa DESPUÉS - ideal para logging."

Concepto crítico

Exit Codes - Memorizar:
• exit 0 = PERMITIR la acción
• exit 2 = BLOQUEAR la acción
• Otros códigos = Error, Claude decidirá

🔄 Diagrama: Flujo de Hooks
Usuario pide acción │ ▼ ┌─────────────┐ │ PreToolUse │──── exit 2 ────► BLOQUEADO │ (hook) │ └──────┬──────┘ │ exit 0 ▼ ┌─────────────┐ │ ACCIÓN │ (Bash, Write, Read, etc.) │ EJECUTADA │ └──────┬──────┘ │ ▼ ┌─────────────┐ │ PostToolUse │──── (log, notify, etc.) │ (hook) │ └─────────────┘
📢 Cómo narrar este diagrama:
  1. "El usuario pide algo, como ejecutar un comando bash"
  2. "PreToolUse intercepta ANTES" - Señala el primer hook
  3. "Si retorna exit 2, se bloquea completamente" - Muestra la flecha a BLOQUEADO
  4. "Si retorna exit 0, la acción procede" - Sigue la flecha hacia abajo
  5. "Después de ejecutar, PostToolUse puede loggear o notificar" - Señala el último hook
Demo en vivo - Hook de validación 
#!/bin/bash
# .claude/hooks/validate-bash.sh
# El JSON del evento llega por STDIN, no por argumentos

INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')

# Bloquear comandos peligrosos
DANGEROUS=("rm -rf /" "rm -rf ~" "> /dev/sda")

for pattern in "${DANGEROUS[@]}"; do
    if echo "$COMMAND" | grep -qE "$pattern"; then
        echo "BLOCKED: Comando peligroso detectado"
        exit 2  # BLOQUEAR
    fi
done

exit 0  # PERMITIR
Configurar en settings.json 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/validate-bash.sh" }
        ]
      }
    ]
  }
}

💡 Demo impactante: Intenta ejecutar rm -rf /tmp/test (inofensivo pero parece peligroso) y muestra cómo el hook lo bloquea. Esto genera un "¡wow!" en los participantes.

🔍 Deep Dive: Qué recibe realmente un hook
▼

Aclaración importante: no existen variables de entorno $TOOL_NAME / $TOOL_INPUT / $TOOL_OUTPUT. El hook recibe un JSON completo por stdin (léelo con INPUT=$(cat) y parséalo con jq):

  • .tool_name - Nombre de la herramienta (Bash, Write, Read...)
  • .tool_input - Objeto JSON con los parámetros de entrada
  • .tool_response - (Solo PostToolUse) Resultado de la ejecución
  • .session_id - ID único de la sesión

${CLAUDE_PROJECT_DIR} sí es una variable de entorno real — apunta a la raíz del proyecto y es la forma recomendada de referenciar el script del hook en command.

5 Hooks - Lifecycle Completo

15 min ▼
⏱️ Distribución: 5 min diagrama | 7 min demo | 3 min discusión
🔄 Diagrama: Lifecycle Completo de Sesión
┌──────────────┐ │ SessionStart │ ─► Inicializar ambiente, cargar estado └──────┬───────┘ │ ▼ ┌──────────────────┐ │ UserPromptSubmit │ ─► Validar/enriquecer el prompt └──────┬───────────┘ │ ▼ ┌─────────────┐ ┌─────────────┐ │ PreToolUse │ ───► │ TOOL USE │ └─────────────┘ └──────┬──────┘ │ ▼ ┌─────────────┐ │ PostToolUse │ ─► Log, validar resultado └──────┬──────┘ │ ◄────────────────────┘ (loop mientras haya trabajo) │ ▼ ┌─────────────┐ │ SessionEnd │ ─► Limpiar, persistir estado └─────────────┘
📢 Cómo narrar este diagrama:
  1. "SessionStart se ejecuta al abrir Claude Code, pero no solo ahí" - También dispara en --resume/--continue, /clear y compactación automática. Claude Code distingue el caso con el campo start_reason del JSON (valores: startup, resume, clear, compact, fork) - úsalo para cargar dependencias, verificar ambiente
  2. "UserPromptSubmit intercepta cada mensaje del usuario" - Puedes detectar intenciones peligrosas aquí
  3. "El loop de PreToolUse → Tool → PostToolUse se repite muchas veces" - Una por cada acción
  4. "SessionEnd al cerrar la sesión completa" - Persiste estado, genera resúmenes. Aclara que "Stop" es un evento distinto (dispara una vez por respuesta de Claude, no al cerrar la sesión) — un error común es confundirlos.

💡 Caso de uso real: Un SessionStart que verifica que todas las dependencias de Python estén instaladas, y un SessionEnd que genera un resumen de lo que se hizo en la sesión.

Demo en vivo - Simular el lifecycle sin esperar eventos reales 
echo '{"session_id": "test123"}' | .claude/hooks/session-start.sh
cat .claude/logs/session_test123.json   # status: "active"

💡 Por qué importa esta demo: a diferencia de PreToolUse/PostToolUse (Tema 4), SessionStart y SessionEnd solo disparan de verdad al abrir/cerrar Claude Code — simularlos con echo | script.sh deja probar la lógica del script sin reiniciar sesiones en vivo. Al final, sí abre una sesión real una vez para mostrar que el JSON de sesión se crea y se completa solo.

🔍 Deep Dive: Qué hace realmente echo '...' | .claude/hooks/session-start.sh
▼

Es la pregunta que más confusión genera en este tema, así que vale la pena narrarla despacio. Cuando Claude Code dispara de verdad el evento SessionStart, internamente hace dos cosas: (1) ejecuta el comando que pusiste en settings.json como un subproceso, y (2) le escribe el JSON del evento a la entrada estándar (stdin) de ese subproceso, tal como tú harías con algo | comando.

echo '{"session_id": "test123"}' | .claude/hooks/session-start.sh reproduce exactamente ese mecanismo a mano:

  • echo '...' escribe el texto JSON a su propia salida estándar (stdout)
  • el pipe | conecta esa salida a la entrada estándar del script
  • dentro del script, INPUT=$(cat) lee todo stdin hasta que se cierra y lo guarda en una variable

El script no tiene forma de distinguir si ese JSON vino de Claude Code de verdad o de tu echo manual — para el script, ambos casos son idénticos: "algún proceso me escribió texto JSON por stdin y cerró la tubería". Por eso la simulación es fiel y sirve para depurar la lógica sin abrir/cerrar sesiones reales.

Qué SÍ es distinto al simular a mano:

  • ${CLAUDE_PROJECT_DIR} (usado en settings.json para ubicar el script) no se sustituye — por eso al probar a mano llamas al script por su ruta relativa/absoluta directamente, y debes correr el echo desde la raíz del repo para que mkdir -p ".claude/logs" caiga donde esperas.
  • El JSON real trae más campos de los que usas: cwd, transcript_path, hook_event_name y start_reason. El ejercicio solo lee session_id, pero en un hook de producción normalmente sí revisas start_reason para no repetir trabajo innecesario en cada /clear.

Un detalle que sorprende en clase: SessionStart es uno de los pocos eventos (junto con UserPromptSubmit) donde el stdout con exit code 0 no se descarta — Claude lo recibe como contexto real que puede leer y usar. Por eso load_previous_state() hace cat "$STATE_FILE" en vez de solo loguearlo: ese cat es literalmente cómo Claude "se entera" del estado de la sesión anterior. En la mayoría de los demás hooks, ese mismo echo solo iría a un debug log invisible.

Nombres 100% arbitrarios: ni session-start.sh, ni la extensión .sh, ni la carpeta .claude/hooks/ son requisitos de Claude Code — son pura convención del curso para que sea legible. Lo único que importa es el campo command en settings.json: podría apuntar a un script Python, un binario compilado o un archivo en cualquier ruta, siempre que lea JSON de stdin.

Claude Code cachea automáticamente prefijos de prompts repetidos. Esto significa que si tu CLAUDE.md y contexto del proyecto son los mismos entre requests, pagas menos tokens.

Para maximizar el cache:

  • Estructura los prompts con prefijo común
  • Evita información dinámica al inicio del prompt

🔍 Deep Dive: Fork vs Subagent Nuevo
▼

Este es un concepto NUEVO para muchos instructores. Aquí va una guía completa:

¿Qué es un Fork?

Un Fork es un subagent que hereda toda tu conversación actual — toda la historia, contexto, archivos leídos, instrucciones dadas. Es como si clonaras tu sesión actual en un proceso paralelo independiente.

Analógico: Es como enviar a tu asistente a investigar algo en una sala separada, pero lleva TODOS tus apuntes, el CLAUDE.md, todo — mientras tú sigues trabajando aquí sin que lo que haga allá contamine tu contexto.

¿Qué es un Subagent Nuevo?

Un Subagent Nuevo es una sesión completamente limpia. Se le da SOLO el prompt que necesita, nada más. No ve tu conversación, no hereda CLAUDE.md, es una hoja en blanco.

Analógico: Es como contratar a un especialista externo específicamente para "validar este CSV". Le das la instrucción y el archivo, nada más. No necesita saber tu contexto.

Ejemplos Prácticos

Usar FORK:

"Necesito que investigues en paralelo si existe una librería Python para gráficos 3D interactivos. No necesito una respuesta específica — explora, lee documentación, propón opciones. Te dejo el contexto completo de nuestro proyecto."

Usar SUBAGENT NUEVO:

"Valida que data/ventas_2024.csv tenga estructura correcta, sin nulos en campos críticos, precios positivos, cantidades > 0."

Regla Práctica para el Instructor

Si tienes DUDA: Usa Subagent Nuevo para tareas paralelas (especialistas independientes), y Fork solo para investigación abierta que necesita TODO tu contexto.

La razón: Subagent nuevo = más barato, más rápido, y se paraleliza bien. Fork = más caro, más lento, pero mejor para research explorador.

P: "¿Por qué no simplemente usar un solo Claude y que haga todo?"

R: Porque:

  • Velocidad: 3 tareas en paralela toman el tiempo de la más lenta, no la suma
  • Contexto: Un Claude con 100k tokens en contexto es más lento y caro que 3 con 20k
  • Calidad: Un especialista (Validator con Haiku) es mejor que un generalista
  • Costo: Haiku (validación) es 5x más barato que Sonnet (análisis)

P: "¿Cuándo uso Fork y cuándo Subagent Nuevo?"

R: Regla de oro:

  • Fork: Cuando el subagent NECESITA saber TODO. Ej: "Investigar si existe solución a X, dados nuestros constraints"
  • Subagent Nuevo: Cuando la tarea es independiente. Ej: "Valida este CSV", "Genera este reporte"

Tip: 90% de las veces quieres Subagent Nuevo. Fork es raro.

P: "¿Qué pasa si los 3 subagents necesitan comunicarse?"

R: Eso es Agent Teams (Tema 8). Los subagents de Tema 7 reportan al orquestador (tú). Agent Teams permiten que se comuniquen entre sí directamente.

P: "¿Cómo sé que el Subagent Nuevo no ve mi CLAUDE.md?"

R: No lo ve porque nace limpio. Solo recibe el prompt que le das. Ventaja: contexto controlado. Desventaja: no hereda reglas del proyecto (pero eso es a propósito — quieres que sea independiente).

Si necesita que un subagent herede CLAUDE.md, eso es un Fork.

P: "¿Cuántos subagents puedo lanzar en paralela?"

R: Sistema limita a ~16 concurrentes. Pero prácticamente, 3-5 en paralela es ideal. Más de eso es raro (y caro).

8 Agent Teams y Comunicación Peer-to-Peer

20 min ▼
⏱️ Distribución: 5 min concepto | 6 min arquitectura | 4 min demo | 5 min ejercicio
Si vas justo de tiempo, recorta el diagrama — pero NO recortes el matiz de authority ni el "¿dónde va el handoff?". Son las dos preguntas que llegan por correo después.

📖 Primer para el instructor (léelo ANTES de dar el tema):

Hay tres cosas del material que van a generar preguntas y que tienes que tener clarísimas, porque si las respondes mal enseñas algo falso:

1. message es un STRING, no un objeto. La firma real es {"to": "...", "summary": "...", "message": "..."}. Cuando envías un payload JSON va envuelto en JSON.stringify(...). Dilo explícitamente la primera vez que muestres un SendMessage, o alguien copiará el código y fallará.

2. La dirección de un agent es su agentId, no el nombre del type. extractor es el nombre de una definición; el spawn devuelve el id de la instancia. Y los subagents hermanos no se alcanzan entre sí: el peer-to-peer real de SendMessage vive entre sesiones de Claude Code. Dentro de una sesión, el agente principal es el coordinador que releva cada payload.

3. authority: can-block y teammates: NO son campos de runtime. Claude Code interpreta name, description, tools y model. El resto es convención documental que el modelo lee y respeta — no algo que el sistema imponga. Esto no es un detalle menor: es la lección del tema sobre qué garantías te da cada mecanismo.

El marco mental que quieres dejar instalado:

HOOK      → bloqueo GARANTIZADO   (lo ejecuta el harness)
tools:    → bloqueo ESTRUCTURAL  (no tiene la herramienta, punto)
authority:→ bloqueo COOPERATIVO  (el modelo decide obedecer)

Si un alumno pregunta "¿entonces para qué sirve authority?": sirve, y el modelo lo respeta — pero sabe qué garantía compraste. Diseño robusto usa las tres capas.

Qué decir al comenzar

"En el tema anterior, los subagents hacían una tarea puntual y te reportaban. Ahora vamos un paso adelante: un Agent Team, varios especialistas encadenados en un pipeline de etapas, donde el resultado de uno es la entrada del siguiente. Piénsenlo como una cadena de montaje: cada estación recibe una pieza, hace lo suyo, y la pasa. Y presten atención a una pregunta que vamos a responder con precisión: ¿quién puede hablarle a quién?"

🎯 Por qué es importante: Esta es la diferencia entre delegar una tarea (Tema 7) y diseñar un flujo de N etapas con especialistas (Tema 8). Cada agent tiene su propio modelo, sus propias tools y su propia ventana de contexto — y ese aislamiento es a la vez la ventaja y el costo.

Concepto: Diferencia Tema 7 vs Tema 8
Tema 7 - Subagents (delegación puntual)
TÚ (orquestador)
   ↓
[Spawn Subagent A] → Trabajo A ← Reporta resultado
   ↓
[Spawn Subagent B] → Trabajo B ← Reporta resultado
   ↓
[Procesar resultados juntos]

✓ Tareas independientes, sin orden entre ellas
✓ Control centralizado
Tema 8 - Agent Team (pipeline de etapas)
TÚ = COORDINADOR

[extractor] ──payload──► TÚ ──► [transformer] ──payload──► TÚ
                                                            │
                                              ──► [loader] ─┘
                                                    │
                                    TÚ ──► [quality-checker] en cada etapa

✓ El resultado de cada etapa alimenta la siguiente
✓ Especialistas con modelo y tools propios
✓ El coordinador releva; los agents no se hablan entre sí

Di esto explícitamente: "los cuatro agents son hermanos, hijos del principal. Un SendMessage de uno a otro falla con no reachable. El peer-to-peer real de SendMessage existe — pero entre sesiones de Claude Code, no entre subagents de una misma sesión."

💡 Caso de uso real: un data pipeline de 1000 archivos. El coordinador puede lanzar la extracción del archivo N+1 mientras el transformer aún trabaja en el N. Con un solo agente secuencial esperarías cada paso.

Patrón: Handoff Protocol (Avanzado)

❓ Pregunta que SIEMPRE sale aquí: "¿dónde va ese código?"

Adelántate y respóndela antes de que la hagan. La confusión es real y bloquea el resto del tema:

El handoff no es un archivo nuevo ni código suelto. Es un formato de payload que se documenta dentro del body de un agent .md, en su sección "Cómo Entregas tu Trabajo". Es el mismo traspaso de los pasos anteriores, con un contenido más rico. Y es opcional — el pipeline del ejercicio funciona sin él.

"A veces un agent quiere transferir completamente su tarea a otro. Ese es el patrón 'handoff'. Pero antes de ver el formato, la pregunta importante: ¿por qué necesitaría un payload tan gordo?"

"Porque cada agent corre en su propia ventana de contexto. El transformer no ve nada de lo que hizo el extractor — ni los archivos que leyó, ni las decisiones que tomó, ni los errores que sorteó. Si su tarea está fija de antemano, tres campos bastan. Si tiene que decidir algo, necesita el contexto completo o improvisa a ciegas."

Contrasta las dos cosas en la pizarra — esto es lo que hace clic:

─────────────────────────         ─────────────────────────
{data_file, row_count}            + qué se hizo
                                  + qué falta
                                  + restricciones
                                  + artifacts

"Ya sabes tu trabajo"             "No tienes mi contexto"
Tarea predefinida y fija          Tarea abierta (tú decides cómo)
Traspaso rutinario                Transfiere la responsabilidad entera

"El ejemplo ETL es didáctico. Pero ustedes escriben código, no pipelines de datos todo el día. ¿Cuándo vale la pena montar un team? Recuerden que cada agent es una ventana de contexto extra — tiene que ganarse el gasto."

✅ Los cuatro casos donde un team sí paga (menciona 2-3, no los cinco):

  • Migración a escala — un agent descubre los call sites, N agents transforman en paralelo (cada uno en su worktree), un verifier corre tests. El caso canónico: el trabajo no cabe en un solo contexto.
  • Code review multi-ángulo — security / perf / test-coverage revisan el mismo diff sin verse entre sí, y un verifier intenta refutar cada hallazgo. La independencia ES el producto: un solo agente ancla en lo primero que encontró y deja de buscar.
  • Implementar → probar → arreglar — el tester no debe ver el razonamiento del implementer, o hereda sus puntos ciegos y valida los mismos supuestos equivocados.
  • Debug distribuido — un agent por servicio/log. Ningún contexto único aguanta los logs de cinco servicios.

❌ Y di explícitamente cuándo NO: refactors de un archivo, features pequeñas, y sobre todo cualquier flujo donde el paso B necesite ver todo lo del paso A. Ahí el aislamiento es puro costo.

📜 La regla que se llevan

Un Agent Team GANA cuando el aislamiento de contexto
es una VENTAJA:  independencia · paralelismo · volumen

PIERDE cuando el aislamiento es un obstáculo a superar.

❓ Preguntas Frecuentes del Tema 8

P: "¿Dónde pego el código del handoff? ¿Es un archivo nuevo?"

R: No es archivo ni código suelto — es un formato de payload que documentas dentro del body de un agent .md, en su sección "Cómo Entregas tu Trabajo". Y es opcional: el pipeline funciona sin él. Sirve cuando el receptor tiene que decidir algo, no solo ejecutar un paso fijo.

P: "¿authority: can-block realmente bloquea?"

R: No a nivel de runtime. Claude Code interpreta name, description, tools y model; el resto es convención documental. Funciona porque el agent lee su propio prompt y coopera. Si necesitas bloqueo garantizado, eso es un hook (PreToolUse, Tema 4) — lo ejecuta el harness, no el modelo. Y la autoridad estructural real está en tools:: nuestro quality-checker no tiene Write, así que no puede modificar datos coopere o no.

P: "¿Qué otros valores de authority existen?"

R: Los que tú inventes — es convención, no una enum del sistema. Útiles: advisory (solo reporta), can-escalate (sube al humano tras N fallos), can-retry, read-only. Lo importante es que el body del agent explique qué significa, porque ahí es donde el modelo lo lee.

P: "Copié el SendMessage del ejemplo y falla."

R: Dos causas, por orden de frecuencia. (1) El destino: to quiere el agentId de una instancia viva o reanudable, no el nombre del type. (2) El tipo de message: recibe un string, así que envuelve el objeto en JSON.stringify(...).

P: "¿Cuál es la diferencia real con los subagents del Tema 7?"

R: El Tema 7 es delegación puntual: tareas independientes, sin orden entre ellas. El Tema 8 es un flujo con etapas: el resultado de una alimenta la siguiente, con especialistas de modelo y tools distintos y un supervisor que puede detenerlo. Si tu flujo tiene 2-3 pasos y tú puedes coordinarlos a mano, usa Tema 7 — es más simple de depurar. Un Team gana con N etapas, paralelismo real, o cuando quieres opiniones independientes.

P: "¿Cómo depuro esto cuando falla a mitad del pipeline?"

R: Ahí está el costo real de teams y vale la pena decirlo en clase: cada agent tiene su propio transcript. Tu ventaja es que el coordinador ve todos los payloads — esa es tu traza, y por eso conviene que cada etapa devuelva conteos (rows_in, row_count) además de rutas. Y por eso existe el patrón de dead-letter queue: un payload que nadie procesa desaparece en silencio si no lo capturas.

P: "Ya creé los 4 agents y el skill. ¿Cómo lo corro?"

R: /run-pipeline. Y aprovecha para aclarar la confusión más común del tema: los bloques de código del SKILL.md no son código que se ejecute. Un skill son instrucciones para el agente principal — Claude lo lee y hace las llamadas reales. Nadie interpreta ese pseudocódigo.

P: "ListAgents me dice 'No reachable agents'. ¿Configuré algo mal?"

R: No, es correcto. Los .md son definiciones (agent types), no procesos. ListAgents lista instancias vivas; si no lanzaste ninguna, está vacío. Para ver las definiciones cargadas: /agents. Es la distinción que más cuesta y conviene provocarla con una pregunta antes de correr nada.

P: "¿Por qué mi extractor no puede enviarle nada al transformer si lo tengo en teammates?"

R: Porque teammates: documenta el grafo del pipeline, no crea rutas de mensajería — los 4 agents son hermanos, hijos del principal, no peers. Además ninguno espera: cada uno ejecuta su prompt y termina. Por eso el diseño del ejercicio es que cada agent devuelva su payload JSON y el coordinador lo releve por agentId.

P: "Entonces, ¿el peer-to-peer del Tema 8 no existe?"

R: Existe — pero no entre subagents hermanos. SendMessage entre peers funciona entre sesiones de Claude Code (dos terminales, o sesiones en la nube — se descubren con ListAgents). Es una distinción honesta que vale más que el ejercicio: sepan qué garantía tienen antes de diseñar sobre ella.

P: "Envié el mensaje, dijo 'queued', y el agent nunca lo procesó."

R: Encolado ≠ entregado. Un mensaje a un agent vivo se entrega "at its next tool round"; si el agent termina su turno antes de ese round, el mensaje se queda sin consumir. Por eso la regla práctica es verificar el artefacto en disco, no confiar en el acuse. Este es exactamente el agujero que justifica la dead-letter queue del Tip Avanzado — buen momento para conectarlo.

9 MCP (Model Context Protocol) Integration

20 min ▼
⏱️ Distribución: 4 min concepto | 6 min demo filesystem | 5 min server custom | 3 min permisos | 2 min cierre

📖 Primer para el instructor (léelo antes de dar el tema):

MCP es un protocolo cliente-servidor. Claude Code es el cliente; un "MCP server" es un proceso independiente que Claude arranca y con el que habla por stdin/stdout usando JSON-RPC. El server publica dos cosas:

  • tools — funciones que Claude puede llamar (con un JSON Schema de entrada)
  • resources — datos que Claude puede leer como contexto (identificados por una URI)

La analogía que funciona en clase: "un MCP server es un driver USB. Antes, cada integración era un cable propietario. Ahora todos hablan el mismo protocolo, así que cualquier herramienta se conecta a cualquier cliente."

Lo único que debes tener perfectamente claro: dónde vive la configuración (.mcp.json, NO settings.json) y cómo se llaman las herramientas resultantes (mcp__<server>__<tool>). Todo lo demás se deriva de ahí.

Qué decir al comenzar

"Hasta ahora Claude solo ha tocado archivos locales. Pero el trabajo real vive en otro lado: la base de datos, el data warehouse, Slack, Jira. MCP es el protocolo estándar para conectar todo eso. En lugar de escribir una integración custom para cada servicio, expones un 'server' y Claude descubre sus herramientas solo. Piénsenlo como plugins estandarizados — o como drivers USB: un solo protocolo, cualquier periférico."

❓ Preguntas típicas de este tema
¿Un MCP server puede estar escrito en Python?
Sí. El protocolo es agnóstico del lenguaje; hay SDK oficial para Python, TypeScript y otros. Lo único que importa es que hable JSON-RPC por stdio (o HTTP/SSE). En el curso usamos Node porque el SDK de JS es el que más ejemplos tiene.
¿Cuál es la diferencia entre un MCP server y un Skill?
Un Skill son instrucciones para Claude (qué hacer y en qué orden); un MCP server son capacidades nuevas (poder hacer algo que antes no podía). Regla de Oro: SKILL = lo que el agente debe saber; MCP = integración con servicios externos. Un skill puede orquestar varias tools MCP — eso es exactamente el ejercicio del Paso 6.
¿Los subagents tienen acceso a las herramientas MCP?
Sí, si las declaran en su frontmatter tools:. Y heredan los permisos del proyecto: si el deny bloquea una tool, la bloquea también para los subagents.
¿Qué pasa si el server se cae a mitad de una sesión?
Las llamadas a sus tools fallan con error; Claude lo reporta y sigue. No tumba la sesión. Por eso en el skill del ejercicio insistimos en el manejo de errores: "si get_metrics falla, marca esa fila como no disponible y continúa".
¿Puedo poner el token directamente en .mcp.json si el repo es privado?
No. Un repo privado sigue siendo un repo: queda en el historial de git, en los clones de todo el equipo y en cualquier backup. Usa ${VARIABLE}. Es la misma cantidad de trabajo.

10 RAG Básico - Chunking y Embeddings

20 min ▼
⏱️ Distribución: 5 min concepto | 4 min demo embeddings | 6 min construir el pipeline | 3 min skill | 2 min cierre

📖 Primer para el instructor:

Un embedding es una lista de números (aquí, 384) que representa el significado de un texto. Textos con significado parecido dan vectores cercanos, aunque no compartan ni una palabra. La "cercanía" se mide con similitud coseno: 1.0 = idénticos en significado, 0 = sin relación.

RAG son cuatro pasos y nada más: (1) partir los documentos en trozos, (2) convertir cada trozo en vector, (3) guardar los vectores, (4) al preguntar, convertir la pregunta en vector y traer los trozos más cercanos. Todo lo demás — reranking, índices, híbrida — son mejoras sobre estos cuatro pasos.

Qué NO necesitas saber: cómo se entrena el modelo de embeddings, ni la matemática de la red neuronal. Si alguien pregunta, la respuesta honesta es: "es un modelo entrenado para que textos parecidos den vectores parecidos; lo usamos como caja negra y lo evaluamos midiendo recall (Tema 14)".

Qué decir al comenzar

"RAG resuelve un problema fundamental: Claude no puede 'recordar' todo su proyecto. Meter toda la documentación en el prompt es caro e imposible para proyectos grandes. En lugar de eso, indexamos los documentos y recuperamos solo los fragmentos relevantes para cada pregunta. Es como darle a Claude acceso a una biblioteca con un bibliotecario inteligente que sabe exactamente qué párrafo traerle."

📚 Diagrama: Sistema RAG Completo
INDEXACIÓN (una vez, offline) ┌──────────┐ ┌──────────┐ ┌──────────────┐ │Documentos│ → │ Chunking │ → │ Embeddings │ │ (docs/) │ │ (dividir)│ │ (vectores) │ └──────────┘ └──────────┘ └──────┬───────┘ │ ▼ ┌──────────────┐ │ Vector Store │ │ (FAISS) │ └──────────────┘ ▲ CONSULTA (cada pregunta) │ ┌──────────┐ ┌──────────┐ ┌──────┴───────┐ │ Query │ → │ Embedding│ → │ Búsqueda │ │ "¿cómo?" │ │ (vector) │ │ (similitud) │ └──────────┘ └──────────┘ └──────┬───────┘ │ ▼ ┌──────────┐ ┌──────────┐ ┌──────────────┐ │ Respuesta│ ← │ Claude │ ← │ Top-K docs │ │ informada│ │ (genera) │ │ relevantes │ └──────────┘ └──────────┘ └──────────────┘
📢 Cómo narrar este diagrama:
  1. "Hay dos fases: indexación y consulta" — tapa la mitad de abajo con la mano mientras explicas la de arriba
  2. "Indexación se hace UNA VEZ" — o cada vez que cambia la documentación (ahí entra el hook del Tema 5)
  3. "Los dividimos en chunks" — porque documentos enteros no caben y diluyen la señal
  4. "Cada chunk se convierte en un vector" — números que representan significado
  5. "Se guardan en un Vector Store" — hoy un archivo, en el Tema 12 un índice FAISS
  6. "La pregunta también se convierte en vector" — mismo modelo, mismo espacio
  7. "Buscamos los chunks más cercanos" — distancia entre vectores, no coincidencia de palabras
  8. "Claude recibe solo esos chunks" — 5 párrafos, no 500 páginas. Ahí está el ahorro
Demo clave (hazla en vivo, son 20 segundos y lo explica todo) 
python -c "
from src.rag.embeddings import get_embedding, cosine_similarity
a = get_embedding('las ventas de laptops crecieron en el norte')
b = get_embedding('el volumen de portátiles subió en la región norte')
c = get_embedding('receta de pastel de chocolate')
print(f'Dimensión: {len(a)}')
print(f'a-b (deben parecerse): {cosine_similarity(a,b):.3f}')
print(f'a-c (no deben):        {cosine_similarity(a,c):.3f}')
"

"Miren las dos primeras frases: no comparten casi ninguna palabra. 'Ventas' contra 'volumen', 'laptops' contra 'portátiles'. Un buscador por palabras clave diría que no tienen nada que ver. El embedding dice 0.7. Y la receta de pastel, que sí comparte estructura gramatical, da 0.1. Eso es lo que compramos con los embeddings: significado, no texto."

🔍 Deep Dive: ¿Qué tamaño de chunk usar?
▼
  • Muy pequeño (100-200 chars): pierde contexto, frases sueltas sin sentido. El vector representa una idea incompleta
  • Muy grande (2000+ chars): mezcla varios temas en un solo vector, que acaba siendo "el promedio" de todos y no se parece a ninguno. Además gasta tokens de contexto
  • Ideal (400-800 chars): párrafos completos con contexto suficiente
  • Overlap (50-100 chars): evita cortar una idea justo a la mitad entre dos chunks
  • Mejor que ajustar el tamaño: respetar la estructura. Nuestro chunk_markdown corta por secciones (#), lo que casi siempre supera a cortar por número de caracteres
🔍 Deep Dive: por qué el threshold del curso es 0.2 y no 0.5
▼

11 RAG Avanzado - Hybrid Search y Reranking

20 min ▼
⏱️ Distribución: 4 min problema | 5 min BM25 e híbrida | 5 min reranking | 4 min pipeline | 2 min discusión

📖 Primer para el instructor:

  • BM25 es el algoritmo clásico de búsqueda por palabras (el que usan Elasticsearch y Lucene). Puntúa un documento por cuántas veces aparecen los términos de la query, penalizando términos muy comunes (IDF) y documentos muy largos. No entiende significado — y por eso es perfecto para códigos, siglas y nombres propios, donde el significado no ayuda.
  • Búsqueda híbrida = correr las dos búsquedas, normalizar sus puntajes a [0,1] (porque están en escalas distintas) y sumarlos con un peso alpha.
  • Reranking = segunda pasada, más cara y más precisa, solo sobre los ~20 candidatos que sobrevivieron. Un cross-encoder mira la query y el documento juntos; los embeddings los miran por separado. Por eso captura relaciones que dos vectores independientes no pueden.

La analogía de dos pasos: "primero un filtro rápido que se queda con 20 de 10.000, después un examinador lento que ordena esos 20 bien. Nadie puede permitirse el examinador lento sobre 10.000."

Qué decir al comenzar

"La búsqueda semántica es poderosa pero tiene un punto ciego. Si buscan 'PostgreSQL connection timeout', puede traerles documentos sobre 'problemas de latencia de base de datos' —semánticamente parecidos— y perder el runbook que dice literalmente esas tres palabras. Los términos técnicos, los códigos de error y los nombres propios son exactamente donde la semántica falla y las palabras clave ganan. La búsqueda híbrida usa las dos."

🔀 Diagrama: Búsqueda Híbrida
Query: "PostgreSQL timeout" │ ┌───────────────┴───────────────┐ │ │ ▼ ▼ ┌────────────────┐ ┌────────────────┐ │ SEMANTIC │ │ KEYWORD │ │ (embeddings) │ │ (BM25) │ └───────┬────────┘ └───────┬────────┘ │ │ │ "database issues" │ "PostgreSQL timeout" │ "connection problems" │ "timeout error" │ "latency errors" │ "PostgreSQL config" │ │ └───────────────┬───────────────┘ │ ▼ ┌────────────────┐ │ NORMALIZAR │ scores a [0,1] │ + FUSIONAR │ alpha*sem + (1-alpha)*kw └───────┬────────┘ ▼ ┌────────────────┐ │ RERANK │ cross-encoder sobre el top-20 └───────┬────────┘ ▼ Resultados óptimos
📢 Cómo narrar este diagrama:
  1. "La query va a DOS sistemas distintos" — en paralelo, no en cascada
  2. "Semántica encuentra significado parecido" — aunque no compartan palabras
  3. "Keyword encuentra las palabras exactas" — crítico para términos técnicos
  4. "Normalizar es obligatorio" — el coseno va de 0 a 1, BM25 puede dar 12.7. Sumarlos sin normalizar es sumar peras con kilómetros
  5. "Alpha es la perilla" — 1.0 solo semántica, 0.0 solo keyword, 0.5 balance
  6. "El rerank es la última milla" — reordena el top, no busca de nuevo

🔍 Deep Dive: ¿qué alpha usar en producción?
▼
  • alpha ≈ 0.7-0.8 — documentación en prosa, preguntas en lenguaje natural
  • alpha ≈ 0.5 — mezcla de prosa y referencia técnica. El default sensato
  • alpha ≈ 0.2-0.3 — catálogos, códigos de error, nombres de tablas, SKUs
  • La respuesta honesta: no lo elijas de memoria. Arma 20 preguntas reales con su respuesta correcta (eso es el golden dataset del Tema 14), mide el recall con varios alpha y quédate con el mejor. Cinco minutos de medición valen más que una hora de opiniones.
🔍 Deep Dive: reranking explicado sin matemáticas
▼

Bi-encoder (lo que usamos para buscar): convierte la query en un vector y cada documento en otro, por separado, y compara. Como los documentos se vectorizan de antemano, buscar es instantáneo. Pero el modelo nunca vio la query y el documento a la vez.

Cross-encoder (el reranker): recibe el par (query, documento) junto y emite un puntaje de relevancia. Ve las dos cosas al mismo tiempo, así que capta matices — negaciones, condiciones, "esto aplica solo si...". El costo: hay que ejecutarlo una vez por candidato, así que solo es viable sobre 10-50 documentos.

Frase para clase: "el buscador es un portero que deja pasar a 20; el reranker es el entrevistador que decide el orden de esos 20".

Troubleshooting
No se descarga el modelo cross-encoder
No es problema: el código detecta el fallo e instancia SimpleReranker, una heurística (términos exactos + posición del match + brevedad). La lección pedagógica sigue intacta: el orden cambia tras el rerank. Dilo en voz alta para que nadie crea que "no funcionó".
La híbrida da los mismos resultados que la semántica
Señal de que el corpus no tiene términos técnicos distintivos. Revisa que docs/runbook_incidentes.md esté indexado (python -m src.rag.indexer después de crearlo).
❓ Preguntas típicas de este tema
¿No sería mejor usar directamente Elasticsearch?
Para el componente keyword, sí — en producción probablemente uses un motor real. Aquí implementamos BM25 en 50 líneas para que vean qué hay dentro de la caja, no porque sea la mejor implementación. Lo que se llevan es la arquitectura: dos búsquedas, normalización, fusión, rerank.
¿La query expansion no mete ruido?
Sí, puede. Por eso está limitada a 5 variantes y por eso el rerank viene después: la expansión aumenta el recall (traer más candidatos correctos) y el rerank recupera la precisión. Sin rerank, expandir suele empeorar los resultados.
¿Cuánta latencia añade el reranking?
Con el MiniLM del ejercicio, decenas de milisegundos para 20 candidatos en CPU. Si usaras un LLM como juez, serían segundos y costaría dinero. Es la misma decisión costo/calidad del Tema 6, aplicada a retrieval.
¿Existe algo mejor que la suma ponderada para fusionar?
Sí: Reciprocal Rank Fusion (RRF), que combina por posición en vez de por puntaje. Su ventaja es que no necesita normalizar escalas incompatibles. Está en el "Tip Avanzado" del tema por si alguien quiere ir más lejos.

12 Índices Vectoriales y Optimización

20 min ▼
⏱️ Distribución: 6 min concepto y tipos | 4 min selector | 4 min migración a FAISS | 4 min benchmark en vivo | 2 min matriz de decisión

📖 Primer para el instructor — qué hace cada índice, en una frase:

  • Flat: compara con todos. Exacto por definición, lento por definición. Es la referencia, no un competidor
  • IVF: agrupa los vectores en nlist clusters. Al buscar, solo mira los nprobe clusters más cercanos. Si la respuesta correcta estaba en un cluster que no miró, la pierde — eso es el recall < 100%
  • HNSW: construye un grafo de "vecinos" en varios niveles y navega saltando de nodo en nodo hacia el más parecido. Muy rápido, pero el grafo ocupa mucha RAM
  • PQ (Product Quantization): comprime cada vector en un código corto (de 1536 bytes a 8). Cabe muchísimo más en memoria, a cambio de error
  • IVF-PQ: clusters + compresión. El caballo de batalla para millones de vectores

El concepto que debe quedar: recall@10 = de los 10 vecinos verdaderos, cuántos devolvió el índice aproximado. Es la métrica de calidad de un índice, y siempre se mide contra Flat.

Qué decir al comenzar

"Nuestro vector store funciona para 10.000 documentos. ¿Y con 10 millones? La búsqueda por fuerza bruta compara contra todos: es O(n). Necesitamos índices especializados que sacrifican un poco de precisión por mucha velocidad. Y aquí viene lo importante: esa elección se toma con números, no con intuición. Al final del tema van a tener una función que les recomienda el índice y un benchmark que lo comprueba."

📊 Matriz de Decisión de Índices
┌────────────┬───────────┬───────────┬──────────┬───────────────────┐ │ ÍNDICE │ VELOCIDAD │ PRECISIÓN │ MEMORIA │ CUÁNDO USAR │ ├────────────┼───────────┼───────────┼──────────┼───────────────────┤ │ Flat │ Lento │ 100% │ Baja │ < 10K docs │ │ IVF │ Medio │ 95-99% │ Media │ 10K-1M docs │ │ HNSW │ Rápido │ 98-99% │ Alta │ Cuando hay RAM │ │ IVF-PQ │ Muy rápido│ 92-97% │ Muy baja │ > 1M docs, poca RAM│ └────────────┴───────────┴───────────┴──────────┴───────────────────┘ LA PERILLA DEL TRADE-OFF (IVF): nprobe nprobe = 1 → rapidísimo, recall bajo nprobe = 20 → equilibrio nprobe = nlist → equivale a Flat: recall 100%, sin ventaja
📢 Cómo narrar esta matriz:
  1. "Flat es el baseline" — búsqueda exacta, sin trucos. Todo lo demás se mide contra él
  2. "IVF agrupa vectores similares" — solo busca en los clusters relevantes
  3. "HNSW crea un grafo de navegación" — muy rápido, pero paga en memoria
  4. "IVF-PQ comprime los vectores" — para millones de docs con poca RAM
  5. "95% de precisión significa que 1 de cada 20 veces el mejor resultado no está en el top" — y para un buscador de documentación, eso suele ser perfectamente aceptable. Decidan ustedes, no el default

13 Red Teaming y Pruebas Adversariales

20 min ▼
⏱️ Distribución: 4 min concepto | 4 min suite vulnerable vs defendido | 5 min hook | 4 min ofuscación y defensa en capas | 3 min auditoría

📖 Primer para el instructor:

  • Prompt injection: el input del usuario contiene instrucciones que intentan sustituir a las del sistema. Es el riesgo #1 de OWASP para aplicaciones LLM. No tiene solución perfecta: se mitiga en capas
  • Jailbreak: convencer al modelo de saltarse sus restricciones mediante encuadres ("hipotéticamente", "es para un curso", "eres DAN")
  • Escalación de privilegios: conseguir que ejecute acciones fuera de su permiso, muchas veces encadenando pasos individualmente inocuos
  • Exfiltración: sacar secretos — variables de entorno, claves, archivos sensibles

La idea central del tema, que debe quedar por encima de cualquier detalle técnico: ninguna capa basta sola. El hook por regex es sorteable con ofuscación; la deny-list de permisos no entiende contexto; el juicio del modelo puede ser manipulado. Defensa en profundidad significa que un atacante debe vencerlas todas.

Qué decir al comenzar

"Un sistema de agentes puede fallar de formas que no imaginan. Red teaming es pensar como un atacante para encontrar los agujeros ANTES de que lleguen a producción. Vamos a intentar romper nuestro propio sistema de forma creativa — y después vamos a construir las capas que lo impiden."

🎯 Por qué esta demo es la más importante del tema: el riesgo pedagógico número uno de red teaming es que alguien salga pensando "ya puse el hook, estoy seguro". Romper tu propio hook en vivo, tres minutos después de escribirlo, vacuna contra esa falsa sensación de seguridad mucho mejor que cualquier explicación.

🔍 Deep Dive: por qué el evaluador devuelve tres estados y no dos
▼

_evaluate_response puede devolver True (bloqueado), False (el ataque funcionó) o None (ambiguo, requiere revisión humana).

Ese tercer estado es deliberado y vale la pena señalarlo: una heurística de palabras clave no puede juzgar con certeza si una respuesta libre fue segura. Forzarla a un booleano produce falsos negativos silenciosos — el peor resultado posible en seguridad. Un "no sé, míralo tú" honesto es mejor que un "todo bien" inventado.

Es el mismo principio que aplicarán en el Tema 14 con LLM-as-judge: automatiza lo automatizable y escala lo dudoso a un humano.

14 Evaluación y Testing de Agents

20 min ▼
⏱️ Distribución: 4 min concepto | 4 min golden dataset | 5 min romper algo a propósito | 4 min regresiones | 3 min CI/CD

📖 Primer para el instructor:

Evaluar un agente es como hacer tests unitarios, con una diferencia incómoda: la salida no es determinista. Por eso no se compara con == sino con métricas más laxas:

  • contains / not_contains — la más usada. Robusta y barata. "La respuesta debe mencionar 'auditoría'" / "NO debe contener 'postgresql://'"
  • json_valid — para agentes que deben devolver estructura
  • semantic_similarity — usa embeddings (Tema 10) para comparar significado con un umbral
  • exact_match — solo para salidas verdaderamente cerradas

Golden dataset: el conjunto de casos con su respuesta correcta verificada por un humano. Es el activo más valioso del sistema, y crece cada vez que algo falla en producción: todo bug se convierte en un caso.

Regresión: un caso que antes pasaba y ahora falla. Es distinto de "el pass rate bajó": puedes mejorar el promedio y aun así haber roto justo el caso crítico. Por eso se comparan los ids de los casos, no solo el porcentaje.

Qué decir al comenzar

"Un agent puede funcionar 'bien' en la demo y fallar en producción. La evaluación rigurosa captura edge cases, mide consistencia y establece un baseline. Sin esto, cada cambio es una apuesta: no sabrán si mejoraron o empeoraron el sistema. Y lo peor — no lo sabrán hasta que un usuario lo descubra."

🔍 Deep Dive: cómo escribir buenos casos de evaluación
▼
  • Empieza por los fallos reales. Cada bug de producción se convierte en un caso. Ese es el golden dataset que de verdad protege
  • Cada mitigación del Tema 13 es un caso critical. Es la conexión directa entre los dos temas
  • Prefiere contains sobre exact_match. Un caso que falla porque el modelo dijo lo mismo con otras palabras es ruido, y el ruido mata la confianza en la suite
  • Usa not_contains para seguridad. "La respuesta NO debe contener la cadena de conexión" es objetivo y no admite interpretación
  • Etiqueta desde el día uno. critical para lo bloqueante, regression para lo que ya se rompió antes, y por dominio (rag, format, safety)
  • 20 casos buenos superan a 200 mediocres. Una suite lenta o ruidosa se acaba desactivando, y una suite desactivada vale cero
🔍 Deep Dive: LLM-as-judge — cuándo y con qué cuidado
▼

Hay cualidades que no caben en un contains: ¿el reporte es claro?, ¿el tono es apropiado?, ¿la conclusión se sigue de los datos? Ahí se usa otro modelo como juez, con una rúbrica explícita (por ejemplo 1-5 en fidelidad, completitud y tono).

Las tres reglas que evitan que sea humo:

  1. Valida al juez. Etiqueta 20 casos a mano y comprueba que el juez coincide contigo. Si no coincide, el juez es el problema
  2. Rúbrica explícita. "Puntúa del 1 al 5 según estos criterios" produce resultados mucho más estables que "¿es buena?"
  3. Modelo barato. Haiku basta para clasificar contra una rúbrica; gastar Opus en juzgar suele ser desperdicio (conexión directa con el Tema 6)

❓ Preguntas típicas de este tema
Si el modelo no es determinista, ¿de qué sirve la suite?
Precisamente por eso sirve. No verificas una salida exacta, verificas propiedades: que nunca revele credenciales, que siempre devuelva JSON válido, que cite la convención correcta. Esas propiedades sí deben cumplirse el 100% de las veces, y la variabilidad del modelo hace que probarlas a mano sea inviable.
¿Correr esto en CI no cuesta una fortuna en tokens?
Depende de cómo lo montes. Patrón habitual: en cada commit solo los casos critical (pocos, con el modelo barato); la suite completa una vez al día o antes de release. Y el ejercicio usa un agente simulado justamente para que la infraestructura se pruebe sin costo.
¿Quién escribe y mantiene el golden dataset?
Quien conoce el dominio, no solo quien escribe el código. Los mejores casos salen de las quejas de usuarios y de los incidentes. Es trabajo de producto y de datos tanto como de ingeniería.
¿Qué pass rate es "aceptable"?
La pregunta correcta es otra: cero fallas críticas, siempre. El pass rate global es una tendencia que vigilas; los casos críticos son una compuerta binaria. Un 95% con una falla crítica es peor que un 85% sin ninguna.
